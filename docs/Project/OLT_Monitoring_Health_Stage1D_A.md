# OLT monitoring health — stage 1D-A

Status at preparation: tested local candidate, not deployed. This document describes the release contract; production rollout evidence belongs in the private deployment report.

Monitoring distinguishes process state, a configured VPN interface and route, the last bounded SNMP response, acquisition quality, and per-ONU data freshness/completeness. None substitutes for another. An active service or a preserved snapshot cannot establish a successful hardware read. Missing cache values, unsupported probes, and old unversioned acquisition history are reported as unverified rather than receiving fabricated activity timestamps, counts or latency.

The health reader inspects fixed systemd units and the host IPv4 addresses/main routing table using bounded argument-array processes in the application working directory. The VPN interface is selected by the configured alarm bind address, not the first tunnel or a default peer. Private OLT targets require a matching route through that interface; a public default route cannot establish this path. Interface availability does not assert peer/device reachability or measured latency/loss. Policy routing, other network namespaces, other VPN addressing layouts and unavailable operating-system commands require further validation; unsupported evidence remains unknown.

All dispatcher modes and explicit device runs observe the actual poll return code and read evidence. Poll health is cached separately from customer state. A versioned attempt records start/end, scope, returned state count, known operational states, available optical measurements, and outcome. No observed state, rejected samples, unknown state, missing online Rx, smaller coverage, or selected-port scope cannot become full-device success. An empty result without affirmative empty-port evidence is not assumed successful. Failure caught by an inner poll method propagates into device and cycle reports/history. Existing acquisition, registration writer and snapshot algorithms remain in place.

Native SNMP v1/v2c sysUpTime GETs before and after attempts use a 1.2-second timeout and no retries. Monitoring HTTP reads never send new OLT requests. Three devices therefore add up to six lightweight GETs per full cycle while the path exists; worst-case configured request waits total 7.2 seconds, excluding scheduling/command overhead. A missing route avoids these health GETs. Unsupported SNMP versions stay unverified. A failed probe means no response to that observation, not proof that all customer ONUs are offline.

Attempt metadata is protected by an OLT-scoped cache lock and token so completion of an older attempt cannot replace newer monitoring evidence. The last connection check expires after 180 seconds. A long-running attempt may lose confirmed connection freshness; an old successful check is not kept green indefinitely. Process status comes from systemd independently of cycle completion or pause state. A stopped/unverified process cannot leave an attempt displayed as currently executing.

Data freshness uses per-ONU `sample_observed_at`, with the existing 180-second bound. A fresh snapshot completion time never refreshes an old/undated measurement. Inventory counts include configured and unconfigured entries and distinguish fresh, stale, missing timestamp, unknown state, unresolved identity and Online-without-Rx. Categories may overlap. Freshness does not imply complete operational or optical information. The health reader does not fabricate missing unconfigured metadata or change the writer's decision rules.

Listener service state, heartbeat, recorded bind results, VPN path and packet reception are separate. Neither a running listener nor an SNMP response proves end-to-end alarm delivery. Missing/stale bind evidence remains unknown; one successfully bound socket cannot imply both UDP ports are listening. Existing trusted-source resolution/firewall and customer status remain unchanged.

The monitoring UI presents separate process, VPN, device response, acquisition and data columns, with explicit unknown/partial labels and timestamps. It removes aspirational fixed polling latency and fabricated healthy defaults for this scope. Existing polling controls remain available. Unsupported/absent VPN latency, jitter and loss are unavailable, not zero. This release does not optimize the hardware polling engine, repair VPN reconnect, reconcile customers, guarantee all pages/roles, or update mobile clients.

Validation includes no-cache startup, lost VPN with a recent successful poll, stale observations, partial/failed reads, swallowed return codes, known offline states, Working without Rx, concurrent attempt completion, non-live devices, conflicting identities, malformed legacy cache and listener bind/heartbeat distinctions. Local render checks cover unavailable, failed and partial states. Production preparation loads candidate readers in memory under a database read-only transaction and performs only read-only connection GETs; mutation paths are not run before approval.

Rollout requires a fresh baseline/GitHub check, publication of the exact candidate files, verified database/application/configuration backups, PHP sources and rebuilt web assets, PHP-FPM reload and controlled poller restart. Preserve old hashed assets and both web manifests. Target only monitoring caches when needed; do not flush sessions, identity caches or all Redis. After installing, wait for new versioned attempts and verify actual completed cycles, health states, source/assets, routes/configuration and errors. Do not disconnect production VPN or synthesize customer alarms for validation without a separate agreed test window. Rollback restores only application sources/manifests and reloads workers; never overwrite live operational data with an old database dump automatically.
